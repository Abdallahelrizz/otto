1 What Otto Is

Otto is an AI-native workflow orchestration engine. You build a workflow on a visual canvas — a graph of nodes connected by edges. Otto executes that graph as fast as possible by running independent branches in parallel.

The proof of concept: Cortex Brain (a biologically-inspired AI architecture built by the founder on n8n) ran in 1 minute 49 seconds on n8n and 1.4 seconds on Otto. The ~78× speedup comes from one insight: n8n runs every node one-by-one even when branches are completely independent. Otto uses Promise.all() to run them simultaneously.

The core idea in one line Build a DAG from the workflow JSON → topological walk → Promise.all() on independent nodes → done.

The stack is Node.js + Fastify (backend), React + Vite (canvas frontend in canvas/), Postgres + pgvector (Supabase), and Redis + BullMQ (Railway) for the webhook queue.

4 File 1 — src/engine/dag.js

src/engine/dag.js

A workflow is stored in Postgres as a JSON object with two arrays: nodes and edges. Before any execution, this JSON is handed to dag.js which converts it into three data structures the executor can efficiently walk.

What it builds

StructureTypeContains
nodesMap<id, node>Each node object by its ID
inEdgesMap<nodeId, [{source, sourceHandle}]>For each node: which nodes feed into it and via which handle
outEdgesMap<nodeId, [targetId]>For each node: which nodes it feeds into

Cycle detection

Before returning, dag.js runs a DFS (depth-first search) with three colors: WHITE (unseen), GRAY (in progress), BLACK (done). If it ever visits a GRAY node again, the graph has a cycle — it throws immediately. This prevents infinite loops before execution even starts.

Why sourceHandle matters

The IF node outputs two handles: "true" and "false". When the executor collects inputs for a downstream node, it needs to know which handle the edge came from, so it knows whether to use the "true" output or the "false" output (or SKIP). The sourceHandle field on each edge captures this.

// Simplified structure of what dag.js produces:
// inEdges.get("nodeB") = [{ source: "nodeA", sourceHandle: "true" }]
// This means: nodeB receives its input from nodeA's "true" output handle

5 File 2 — src/engine/executor.js

src/engine/executor.js

This is the heart of Otto. Read it carefully. It contains four functions that work together:

The four functions

fireWorkflow(workflowId, definition, input, triggerType)

Creates an execution record in Postgres immediately, then runs the workflow via setImmediate (non-blocking). Returns the executionId right away so the HTTP response can return immediately. Used by the canvas Run button.

runWorkflow(workflowId, definition, input, triggerType)

Runs the workflow synchronously — awaits completion before returning. Used by saved workflow execution and the BullMQ worker. Returns the outputs of all nodes.

executeDAG(dag, input, executionId, workspaceId)

This is the parallel execution engine. The key idea: every node gets a memoized Promise. When a node needs to run, it first waits for all its dependency promises via Promise.all(deps). Because JavaScript's event loop handles all of these concurrently, nodes with no shared dependencies start and run simultaneously without any coordination code.

// Conceptual model of executeDAG:
nodePromise(id) = async () => {
  const depOutputs = await Promise.all(
    inEdges.get(id).map(dep => nodePromise(dep.source))  // wait for all deps
  );
  return runNode(id, mergeInputs(depOutputs));  // then run this node
}

// All leaf nodes (no deps) start immediately.
// Nodes deeper in the graph automatically wait only for their direct deps.
// No scheduler needed — the Promise chain IS the scheduler.

runNode(node, input, executionId, ...)

Runs a single node. In order: resolve {{ }} expressions in config → fetch credential if needed → call the handler → write logs to Postgres → emit SSE event. This is where errors are caught and written to the execution log.

The SKIP sentinel

When an IF node evaluates to false, the downstream false-branch receives a special SKIP symbol instead of data. In collectInput(), if all of a node's inputs are SKIP, the node itself returns SKIP. This propagates automatically through the entire downstream subgraph — you don't need to add any "skip if upstream skipped" logic to your handlers.

import { SKIP } from '../engine/skip.js';

// A handler can also voluntarily return SKIP:
export async function filterHandler({ input, config }) {
  if (!conditionPasses(config, input)) return SKIP;
  return input;
}

The nodes context

When running, the executor builds a nodesCtx object that maps every already-resolved node ID to its output. This is passed to the expression resolver, enabling {{ nodes.nodeId.field }} in any node's config. You can reference the output of any upstream node by its canvas ID.

6 File 3 — src/nodes/index.js

src/nodes/index.js

This is just a JavaScript Map. It maps a node type string to a handler function. When the executor calls runNode(), it looks up the type in this Map and calls the function it finds.

const handlers = new Map([
  ['webhook_trigger', webhookTrigger],
  ['http_request',    httpRequest],
  ['llm_call',        llmCall],
  ['if',              ifNode],
  // ... 16 more
]);

// If a type isn't in the map, execution throws "Unknown node type: X"

Adding a new node type means: (1) write a handler file in src/nodes/, (2) import it here, (3) add it to the Map. That's the complete backend change.

7 File 4 — src/nodes/if.js

src/nodes/if.js

Read this file to understand the standard node handler contract. Every handler in src/nodes/ follows the same pattern.

Handler signature

export async function ifHandler({ input, rawInputs, config, credential, workspaceId }) {
  // input        — merged output of all upstream nodes
  // rawInputs    — array of { source: nodeId, data } for Merge's collect-array mode
  // config       — the node's settings from the canvas (already expression-resolved)
  // credential   — decrypted credential object (if credentialId was set)
  // workspaceId  — the workspace this execution belongs to

  return result; // plain JS object, or the SKIP symbol
}

What IF does

It evaluates a list of conditions against the input using 10 operators (equals, not-equals, contains, greater-than, less-than, etc.) with AND or OR combining. Based on the result, it returns a special object with two keys:

// IF node output shape:
{
  _ifBranches: {
    "true":  conditionResult ? input : SKIP,
    "false": conditionResult ? SKIP  : input,
  }
}
// The executor's collectInput() reads _ifBranches and routes accordingly.
// The inactive branch gets SKIP, which propagates downstream automatically.

Notice that if.js uses getByPath from src/utils/path.js — a shared dot-path resolver. The same utility is used by expressions.js and filter.js. This is the only significant shared utility in the nodes layer.

8 File 5 — src/routes/executions.js

src/routes/executions.js

This is the HTTP entry point for running a workflow. Understanding this file tells you how a button click on the canvas becomes a running execution.

POST /api/v1/execute — the canvas Run button

// The canvas sends:
{
  definition:  { nodes: [...], edges: [...] },  // inline workflow (unsaved)
  input:       { ... },                          // trigger input data
  triggerType: "manual"
}
// OR if running a saved workflow:
{ savedWorkflowId: "uuid", input: { ... }, triggerType: "manual" }

// Route calls fireWorkflow() → setImmediate → returns immediately with:
{ executionId: "uuid", workflowId: "uuid" }

// Frontend then polls GET /api/v1/executions/:id (or connects to SSE stream)

GET /api/v1/executions/:id/stream — live execution streaming

This endpoint returns Server-Sent Events (SSE). Connect to it with an EventSource in the browser to get real-time updates as each node starts and finishes. The frontend currently polls every 500ms instead — switching to SSE is a pending improvement.

// SSE event types emitted during execution:
{ type: "execution:start", data: { executionId, workflowId } }
{ type: "node:start",      data: { nodeId, nodeName, nodeType } }
{ type: "node:end",        data: { nodeId, status, durationMs, output } }
{ type: "node:skipped",    data: { nodeId } }
{ type: "execution:end",   data: { status, durationMs } }

9 Key Patterns Used Throughout

AES-256-GCM credential encryption

Every time a user stores a credential (API key, SMTP password, etc.), it is encrypted with AES-256-GCM before being written to Postgres. The key is a 32-byte hex string in CREDENTIAL_ENCRYPTION_KEY. The stored shape is { iv, tag, data } — all hex strings. Decryption happens in src/engine/credentials.js at the moment a node needs the credential. The plaintext is never stored, never logged, and never returned by any API.

// Stored in DB (credentials.data column):
{ iv: "hex...", tag: "hex...", data: "hex..." }

// Encrypt (src/utils/encrypt.js):
const { iv, tag, data } = encryptCredential({ apiKey: "sk-..." });

// Decrypt (src/engine/credentials.js — called automatically by runNode):
const { apiKey } = await getCredential(credentialId);

Expression templates

Node configs can contain {{ }} expressions that are resolved at runtime before the handler fires. Two contexts are available:

ExpressionWhat it resolves to
{{ input.field }}A field from the merged input of upstream nodes
{{ input.user.email }}Nested dot-path on the input object
{{ nodes.nodeId.text }}The text field from a specific upstream node's output

ESM throughout

The backend uses ES Modules (import/export), not CommonJS (require). Every import needs the .js extension explicitly — Node.js ESM does not auto-resolve extensions.

// Correct:
import { db } from '../db/client.js';

// Wrong (will throw):
import { db } from '../db/client';

The dotenv first-import rule

import 'dotenv/config' MUST be the very first line of src/server.js. If it isn't, queue/client.js creates the Redis connection before REDIS_URL is loaded from .env, and it silently connects to localhost:6379 instead of Railway — without any error until you actually try to use the queue.

10 Risk Areas & Known Gaps

RiskSeverityDetail
No authentication High Any request can read/write/execute any workflow. The api_keys table exists but the middleware is not wired. Must be added before any public exposure.
Canvas Run bypasses BullMQ Medium POST /api/v1/execute uses setImmediate, not the queue. Failures have no retries. Planned fix: route through executionQueue.add().
Code node is a placeholder Medium The code node throws on execution. The sandbox runtime (isolated-vm vs Docker) was deferred. Any workflow using it will fail at runtime.
schedule_trigger is a pass-through Medium The node exists and won't throw, but no cron runner fires it. Imported n8n scheduled workflows will silently never trigger.
No rate limiting Medium @fastify/rate-limit is not installed. A single client can flood the execution queue. Deferred — add before public launch.
loop runs sequentially Low Loop items are processed one by one (not parallel sub-DAGs per item). Fine for small arrays; will be slow for 100-item batches doing async work.
retry_count always 0 Low BullMQ retry count is never threaded to logNodeEnd. The retry_count column in node_executions is always 0.
memory_patterns embedding Low vector_search queries memory_patterns but nothing writes embeddings to that table yet. Searches will return empty results until a write path exists.
Supabase + local IPv4 Low Supabase free tier direct connection is IPv6-only. Local dev must use the Transaction Pooler (port 6543). Railway supports IPv6 so direct connection (5432) works there.
